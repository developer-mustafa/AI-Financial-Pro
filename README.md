# SpendWise — Personal Finance Tracker

A local-first personal finance manager built with **HTML5, Tailwind CSS, vanilla
JavaScript (ES modules), Chart.js and `Intl`** — no React/Vue/Angular/Svelte/jQuery,
no build-time framework. Data lives in the browser (`localStorage`); an optional
**Cloudflare Worker + NeonDB (PostgreSQL)** backend adds authenticated, multi-device
cloud persistence.

> **Privacy first.** Everything works with no account and no network. Cloud sync is
> opt-in and always goes through the Worker API — database credentials never reach
> the browser.

## Quick start

Requirements: **Node 18+** (Node 20+ recommended) and a modern browser.

```bash
cd spendwise
npm install          # dev deps + the optional backend driver
npm run vendor       # download Chart.js + Lucide into assets/vendor (offline copy)
npm run css:build    # compile Tailwind -> assets/css/app.css
npm run dev          # serve the app on http://localhost:5173
```

Open <http://localhost:5173>.

> **Serve over HTTP.** The app uses ES modules and `fetch`, so opening
> `index.html` via `file://` will not work. Use `npm run dev` or any static server
> (`npx serve .`, `python -m http.server`, …).

`npm run build` runs `vendor` + `css:build` in one go. `assets/css/app.css` and
`assets/vendor/*` are generated artifacts — rebuild them after changing styles or
`scripts/vendor.mjs`.

### First run

The app seeds **default categories and one “Cash” account** only when local storage
is empty, and never re-seeds on later renders. Start by adding income or an expense
with the **+ Add transaction** button (`n` is the keyboard shortcut).

Set `runtime-config.js → apiBaseUrl` to a deployed Worker URL to enable cloud sync
(see [Cloud sync](#cloud-sync-neondb--cloudflare-worker)). Leave it `""` for a
100% offline, local-only experience.

Passwordless sign-in is optional and off by default: point
`runtime-config.js → neonAuthUrl` at your Neon Auth base URL to add an
**Email link** tab to Settings → Cloud sync (see
[Magic-link sign-in](#magic-link-sign-in-optional)).

## Financial rules (the important bits)

These are enforced in one place (`src/utils/calculations.js`) and reused everywhere,
so dashboard totals, account balances, reports and budgets always agree.

1. **Posted only.** Draft/pending rows are visible in lists but excluded from every
   total, balance, report and budget unless `includePending` is passed explicitly.
2. **Transfers are never income or expense.** They move value between two accounts and
   are excluded from income, expense, savings and budget maths.
3. **Refund policy.** A refund is recorded as an **income** transaction (default
   “Refunds” category). Refunds increase income and **never** reduce expenses or budget
   utilisation. Stated verbatim in the UI (Settings → Data & privacy).
4. **Currency.** Totals are computed one currency at a time. Different currencies are
   never added and **no exchange-rate conversion** is performed.
5. **Credit cards.** The ledger is uniform: an expense is an outflow and increases what
   you owe, so a credit-card balance is negative while debt is outstanding. The UI shows
   that signed value as “Owed”.
6. **Money as integer minor units.** Amounts are stored as integers (poisha/cents) and
   formatted with `Intl.NumberFormat`; no floating-point arithmetic on authoritative values.
7. **Dates.** Date-only values are local `YYYY-MM-DD`; ranges are inclusive; there are
   no timezone-induced one-day shifts.

## Data model & persistence

Root state (versioned):

```json
{
  "schemaVersion": 1,
  "transactions": [], "categories": [], "accounts": [],
  "budgets": [], "recurringRules": [], "goals": [],
  "preferences": {},
  "metadata": { "createdAt": "", "updatedAt": "" }
}
```

- **Store.** One plain object; every mutation goes through `store.apply(reason, mutator)`
  which clones a draft, returns the list of changes, then persists and emits
  `data:changed` exactly once. Derived values are never stored — they are recomputed.
- **Storage.** Implemented behind `src/services/storageService.js`
  (`createLocalStorageAdapter`). Missing/malformed data is recovered defensively; quota
  errors are surfaced with a friendly toast; migrations run through `migrate()`.
- **UI preferences** (theme, density, sidebar, alert acknowledgements) are kept in a
  separate `spendwise.ui.v1` key so they never mix with financial records.
- `localStorage` is **not** a vault or a cloud service — it is a convenience store for a
  single browser profile. Use JSON backup/restore or cloud sync to move data.

## Cloud sync (NeonDB + Cloudflare Worker)

Architecture: **frontend → Cloudflare Worker API → NeonDB PostgreSQL**. The browser
only ever knows the Worker’s public URL (`runtime-config.js`). The database connection
string lives in the Worker as the `DATABASE_URL` secret.

1. Read [`backend/README.md`](backend/README.md) for the full deployment guide
   (Neon project, migration, Worker secrets, CORS, smoke tests, rotation).
2. Apply the schema: `cd backend && npm run migrate` (safe, idempotent, `CREATE … IF
   NOT EXISTS` only — it never drops or deletes data).
3. Deploy the Worker and set `DATABASE_URL` + `AUTH_SECRET` as secrets.
4. Put the Worker URL in `runtime-config.js` → `apiBaseUrl` and redeploy the frontend.
5. In the app, open **Settings → Cloud sync**, register/sign in, then **Push** local data
   up or **Pull** it down. Sync is manual and explicit — nothing is silently overwritten.

Sync resources: `transactions`, `categories`, `accounts`, `budgets`,
`recurringRules`, `goals` (the Worker exposes `recurring-rules` over HTTP). Wallet
balance/movement inspection, CSV/JSON import-export and the local-first flow all keep
working with cloud off.

### Magic-link sign-in (optional)

Passwordless sign-in adds an **Email link** tab next to the password form. It is built
on **Managed Better Auth (Neon Auth)** and is entirely optional: with `neonAuthUrl`
empty the tab is not rendered and nothing changes.

How it works:

1. The user enters an email; the browser calls Neon Auth directly
   (`POST <auth>/sign-in/magic-link`). The session lives in an HTTP-only cookie **on the
   auth service**, never in this app.
2. Clicking the emailed link verifies it server-side and redirects back to the app, which
   adopts the session on load (`authService.adoptNeonSession()`).
3. For Worker API calls the app mints a short-lived Neon Auth JWT
   (`GET <auth>/token`, EdDSA/Ed25519, ~15 min) and sends it as a bearer token;
   `authService.getToken()` refreshes it transparently when it is close to expiry.
4. The Worker verifies it **statelessly** against
   `<auth>/.well-known/jwks.json` (cached per isolate, refetched once on an unknown
   `kid`), checking `alg`, signature, `exp`, and `iss`/`aud`.
5. The verified `sub` is mapped to a `users` row: an existing row with the same email is
   linked in place (case-insensitive), otherwise one is created with a **sentinel
   password hash** that can never verify. Magic-link and password sign-in therefore reach
   the same finance data for the same address.

Setup:

1. In the Neon Console: **Settings → Better Auth → Magic Link → Enable Magic Link**
   (set the link expiry, and allow new-user registration if you want sign-ups).
2. Add your app origins under **Trusted origins** (`http://localhost:5173` for local dev;
   `allow localhost` is on by default).
3. Copy the **Auth Base URL** into `runtime-config.js → neonAuthUrl`, and the same value
   into `backend/wrangler.toml → [vars] NEON_AUTH_BASE_URL` (it is a public value, not a
   secret).
4. `cd backend && npm run migrate` to apply `0002_neon_auth.sql` (adds
   `users.neon_auth_user_id` + `users.auth_provider`; additive, non-destructive).
5. Redeploy the Worker and the frontend.

> **Email delivery.** Neon Auth's shared sender (`auth@mail.myneon.app`) is for
> development/testing. Configure custom SMTP in the Console before relying on magic links
> in production.

## Multi-tenancy & platform administration

The application is a **multi-tenant SaaS**: one deployment serves many independent
workspaces. The full model, API and migration plan are documented in
[`backend/README.md`](backend/README.md#multi-tenancy). The essentials:

- **Model.** `Platform → tenants → tenant_members → tenant-owned finance data`. Every
  finance table (`accounts`, `categories`, `transactions`, `budgets`, `recurring_rules`,
  `goals`) has a `tenant_id` that the Worker assigns server-side; `user_id` remains the
  row's author.
- **Two privilege layers, never mixed.**
  - **Platform roles** live on `users.role` (`user` | `admin` = `PLATFORM_ADMIN`). They are
    granted only by a trusted server-side process (the `ADMIN_EMAILS` bootstrap on first
    sign-in, or an existing platform admin) — never by a client, never by public signup.
  - **Tenant roles** live on `tenant_members.role` (`TENANT_ADMIN` | `TENANT_MEMBER`) and
    apply only inside the one workspace they belong to.
- **Server-derived identity.** The authenticated user comes from a verified token and the
  tenant from `tenant_members`. A client-supplied `X-Tenant-Id`, record id or role is
  never trusted: a forged/foreign tenant id is a plain `403`.
- **Isolation in every query.** Lists, reads, updates, deletes, exports and aggregates are
  all constrained by the resolved `tenant_id`. A cross-tenant record returns `404`, never
  another workspace's data.
- **Platform admin** can list/inspect workspaces, change status (activate/suspend/archive),
  manage memberships and read the platform audit log, but does **not** get implicit access
  to a workspace's financial rows — those still require a membership.
- **Tenant admin** manages only their own workspace; the last active workspace administrator
  can never be removed, and no one can change their own role to escape the tenant boundary.
- **Workspace switcher.** Accounts that belong to more than one workspace can switch in the
  top bar; the app flushes pending writes to the old workspace before re-resolving the new
  one, so a save can never land in the wrong dataset.

Setup, endpoints and the migration/rollback procedure live in
[`backend/README.md`](backend/README.md#multi-tenancy).

- Live end-to-end HTTP requests and SQL execution.
- Live in-browser interaction (the harness used a jsdom smoke test instead).

## Security checklist

- ✅ **No credentials in the browser.** `runtime-config.js` holds only a public URL.
  `DATABASE_URL`/`AUTH_SECRET` are Worker secrets only. No secret appears in `index.html`,
  `src/`, `assets/` or any packaged bundle.
- ✅ All database access is server-side, parameterised, and behind auth + tenant
  isolation (every finance query is constrained by the server-resolved `tenant_id`;
  cross-tenant reads return 404, never another workspace's data).
- ✅ **The tenant selector is never trusted.** `X-Tenant-Id` is validated against the
  caller's active membership on every request; a forged/unknown id, a suspended
  workspace or a non-membership returns 403 (no id probing). Absent header → the
  caller's own personal workspace.
- ✅ **No client-supplied identities or roles.** `user_id`/`role`/`tenant_id` are
  always derived from the verified token and the membership row; a platform admin
  gets no implicit access to finance data.
- ✅ **Email verification gate.** A Neon Auth identity is only linked to an account
  after its email is verified (`emailVerified`), closing account-takeover via
  unverified linking.
- ✅ **Soft tenant lifecycle + audit.** Workspaces are suspended/archived, never
  hard-deleted; privileged actions write an append-only audit row that never stores
  credentials, tokens or financial values.
- ✅ SQL identifiers come from hard-coded allow-lists; no raw-SQL endpoint.
- 🟡 **Row-Level Security is deferred (defence-in-depth).** Isolation is enforced in
  the Worker today (one DB role over the Neon HTTP driver); per-tenant RLS policies are
  a planned second layer, not a substitute for the application checks above.
- ✅ **Passwordless sign-in tokens are verified, never trusted.** The Worker checks the
  Neon Auth JWT signature against the published JWKS (Ed25519), plus `alg`, `exp` and
  `iss`/`aud`; a token that claims HS256 is only ever checked with the app secret.
  Auth-service outages fail closed (503) and never fall through to the legacy path.
- ✅ `textContent` for all user-controlled strings; no inline HTML from user input; no
  inline event-handler attributes.
- ✅ Import validation with file-size/record limits; corrupted JSON handled safely; no
  `eval` of user data.
- ✅ Destructive actions (delete, bulk delete, clear data, restore backup) require
  explicit confirmation; a snapshot is taken before a destructive restore.
- ✅ CSV export neutralises spreadsheet formula injection.
- ✅ **Transport & response hardening.** Every API response sets
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY` and HSTS, plus `X-RateLimit-*` headers. A trusted inbound
  `X-Request-Id`/`CF-Ray` is echoed (unsafe values are replaced) so a client error can
  be correlated with the structured server access log without leaking internals.
- ✅ **AI is opt-in and data-minimal.** `/api/ai/*` requires explicit consent, is
  tenant-scoped and rate-limited, and sends only a server-computed aggregate (totals,
  top categories, monthly figures) — never raw transactions, names or emails. The
  Gemini key is a server secret and the model is server-configured.
- ✅ Accessible interactions: labelled fields, focus management and focus trap in
  dialogs, Escape-to-close, reduced-motion support, keyboard-operable controls.

## Known limitations

- **`localStorage` is not unlimited or secure.** It is a single-browser store; large
  datasets, receipts and long histories would need IndexedDB or cloud sync. Keep backups.
- **No automatic cloud synchronisation.** Sync is manual push/pull with an explicit
  source of truth; there is no automatic conflict resolution or background background job.
- **No FX conversion.** Multi-currency totals are shown per currency only.
- **Tenant deletion is soft.** Workspaces can be suspended or archived through the API;
  irreversible hard deletion is deliberately disabled until an approved retention policy
  exists. Deleting a user account still cascades to that user's own rows.
- **Row-Level Security is not enabled.** Isolation is enforced in the query/service layer
  (every statement carries a server-derived `tenant_id`), which was chosen over Postgres
  RLS because the Worker talks to Neon over the HTTP driver with no per-request session
  role/GUC to key policies on. RLS was evaluated and is documented as a possible
  defense-in-depth addition; the current design makes no RLS claim.
- **Recurring rules are reviewed on open** (no server cron). This is deliberate for a
  static app; duplicates are prevented by the occurrence key.
- **Cloud backend is not deployed here.** Worker/Neon steps are documented and unit-tested
  but were not run against live infrastructure (see above).
- **AI is optional, experimental and off until configured.** The `/ai` screen needs
  `GEMINI_API_KEY` set as a Worker secret and a signed-in cloud session; answers are
  general information from an external provider, not financial advice, and are not
  persisted. With no key the endpoints fail closed and the UI shows a sign-in/notice state.
- **Density/theme** are per-device UI preferences, not synced.

## Credential rotation (action required)

A NeonDB connection string was previously pasted in **plaintext in a planning file**.
Treat that credential as **potentially exposed**. It is intentionally **not** reproduced
anywhere in this repository. **Rotate it before any production use** — full steps are in
[`backend/README.md` → Rotating credentials](backend/README.md#rotating-credentials-required).
In short:

1. Reset the Neon role password (or create a new role for `expense-tracker-pro`).
2. Rebuild the connection string with the new password.
3. `npx wrangler secret put DATABASE_URL` (and update `backend/.dev.vars` locally).
4. Redeploy, then verify `GET /api/health` returns `"db":"ok"`.
5. Remove the old value from any planning notes/chat logs and, if it was ever exposed,
   rotate `AUTH_SECRET` too (this invalidates issued tokens).
6. If a **Gemini API key** was ever pasted in plaintext, revoke it in Google AI Studio
   (https://aistudio.google.com/apikey) and set the replacement with
   `npx wrangler secret put GEMINI_API_KEY` — never commit it.
